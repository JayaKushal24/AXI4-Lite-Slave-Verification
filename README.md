# AXI4-Lite-Slave-Verification

## Project Overview

This project implements a SystemVerilog and UVM-based verification environment for an AXI4-Lite (Advanced eXtensible Interface 4 Lite) Slave.

The AXI4-Lite Slave supports read and write transactions using the five independent AXI4-Lite channels. The verification environment is designed to verify channel handshaking, transaction ordering, read/write operation, backpressure, reset behavior, and protocol correctness.

## AXI4-Lite Channels

AXI4-Lite uses five independent channels:

- **Write Address (AW) channel** — Transfers the address for a write transaction.
- **Write Data (W) channel** — Transfers write data and byte strobes.
- **Write Response (B) channel** — Transfers the write response from the Slave to the Master.
- **Read Address (AR) channel** — Transfers the address for a read transaction.
- **Read Data (R) channel** — Transfers read data and the read response from the Slave to the Master.

Each channel uses the `VALID` and `READY` handshake. A transfer takes place when both `VALID` and `READY` are asserted in the same clock cycle.

The AW and W channels are independent, so the write address and write data may be transferred in different cycles or in the same cycle. The Slave generates the corresponding B response after the write transaction is accepted.

For a read transaction, the Slave accepts the address through the AR channel and returns the requested data and response through the R channel.


### Design

The `design/` directory contains the Design Under Test (DUT).

- `axi_dut.sv` — AXI4-Lite Slave RTL design.

### Testbench

The `testbench/` directory contains the complete UVM-based verification environment.

- `axi4_interface.sv` — AXI4-Lite interface connecting the DUT and testbench.
- `axi_agent.sv` — UVM agent containing the driver, monitor, and sequencer.
- `axi_config.sv` — Configuration objects used by the verification environment.
- `axi_driver.sv` — Drives AXI4-Lite transactions onto the interface.
- `axi_environment.sv` — Instantiates and connects the verification components.
- `axi_monitor.sv` — Samples AXI4-Lite transactions from the interface.
- `axi_pkg.sv` — Package containing the AXI4-Lite verification components.
- `axi_scoreboard.sv` — Compares expected and actual DUT behavior.
- `axi_seq_item.sv` — Defines the AXI4-Lite transaction object.
- `axi_sequence.sv` — Contains AXI4-Lite stimulus sequences.
- `axi_sequencer.sv` — Controls transaction flow from sequences to the driver.
- `axi_subscriber.sv` — Collects functional coverage.
- `axi_sva.sv` — Contains SystemVerilog Assertions (SVA) for protocol checking.
- `axi_test.sv` — Defines the UVM test classes.
- `tb_top.sv` — Top-level testbench module.

### Build and Simulation

- `Makefile` — Provides compilation, simulation, and regression targets.
- `README.md` — Project documentation, specification, verification details, and regression information.

## Verification Environment

The testbench is developed using the Universal Verification Methodology (UVM).

The verification environment contains:

- AXI4-Lite interface
- Transaction/sequence item
- Sequencer
- Driver
- Monitor
- Agent
- Environment
- Scoreboard
- Reference model
- Subscriber
- SystemVerilog Assertions
- Test and sequence classes

The scoreboard compares DUT behavior against the expected behavior generated by the reference model.

## Verification Strategy

The verification environment uses:

- Directed testing
- Constrained-random testing
- Protocol assertions
- Functional coverage
- Reference-model-based checking
- Regression testing

## Test Scenarios

The verification plan includes scenarios for:

- AW channel before W channel
- W channel before AW channel
- AW and W handshaking in the same cycle
- Read transactions
- Write transactions
- Simultaneous read and write transactions
- Read-only transactions
- Write-only transactions
- Unaligned reads
- Unaligned writes
- Backpressure
- Reset behavior
- Random AXI4-Lite transactions

## Functional Coverage

Functional coverage is used to measure whether the important protocol and functional scenarios have been exercised.

Coverage includes:

- Transaction types
- AW/W channel ordering
- Handshake behavior
- Backpressure conditions
- Read/write combinations
- Protocol-specific scenarios
